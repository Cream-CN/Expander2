# Expander 用 F# 重写的价值评估

> 日期：2026-11-15
> 评估对象：`D:\expander\Expander-Dev`（Expander / dev worktree）
> 方法：读代码 + 读文档 + 在本机复测运行时与工具链。凡未实测的推断，均在正文标注"未验证"，并集中列在第 7 节。
> 结论口径：只回答"值不值得"，不预设答案；所有数字都给出可复核的来源或假设。

## 0. 结论（先看这里）

**一句话：换语言本身不值这个价；真正值钱的是"把 119 条规则变成可验证的契约"和"把引擎与壳层解耦"，F# 只是做这两件事最顺手的工具之一。**

按资产分层给四档判断：

| 分层 | 规模 | 值不值得用 F# 重写 | 一句话理由 |
|---|---|---|---|
| 引擎（`Header/notation`，92 文件 / 3.2 万行） | 占全部源码 79% | **有条件值得**（不是现在） | 收益真实存在，但 105–160 人日的一次性成本，在单人项目上回收期 6–10 年 |
| CLI（1.8k 行 / 6 条命令） | 4% | **值得，但只能作为迁移的副产品** | 命令面窄、纯文本进出，顺手做掉；单独为它换语言没有意义 |
| GUI（1.8k 行 MFC + 资源/对话框） | 4% | **不值得** | MFC 无法在 F# 里延续，改 Avalonia 是另一笔 30–60 人日且收益最低的重写 |
| 定义文本管线（`defs/*.txt` → `Definitions.h`，966 行生成物） | 2% | **不值得** | 它已经是"数据 → 代码"的生成管线，与语言无关，搬过去只是换个生成器 |

**推荐动作（按性价比排序）：**

1. **立刻做（1–4 天，与语言无关）**：把 `ignore/_refactor_baseline/` 从"一次性快照"升级成"可反复运行的一致性套件"。理由见 §3.6：现有语料已经失效，它现在连回归都跑不了，更不可能当跨语言契约。
2. **立刻做（1–2 天）**：用 F# 写这套套件的驱动/差分工具 + 属性测试。这是本项目里 F# 收益/成本比最高的一块，且完全不碰生产代码。
3. **两周内做（2–4 天）**：3 个代表记号的 F# spike + 决策门指标（§5 阶段 1）。用它把"105–160 人日"和"慢几倍"这两个最大的未知量变成实测数字。
4. **只有决策门通过，才谈引擎迁移**；GUI 全程不动。

**明确不建议：** 现在启动"引擎 + CLI + GUI 全量 F# 化"。这是把三件事（换语言、换前端、换验证体系）绑在一起做，任何一件出问题都会让另外两件白做。

## 1. 盘子有多大（实测数据）

### 1.1 分层规模

| 层 | 文件 | 行数 | 说明 |
|---|---|---|---|
| 引擎 `Header/notation` | 92 | 32,273 | 其中 15 个家族/基座模块 6,290 行，77 个叶子记号 25,983 行 |
| 核心/公共 `Header/core` + `Header/common` | 6 | 469 | `Entry`/`EntryArena`/`Matrix`/`sequence`/`utf8`/`mrssshare` |
| GUI `Expander.cpp` | 1 | 1,788 | MFC/Win32，菜单 + 自绘列表 + 对话框 + 资源 |
| CLI `ExpanderCLI.cpp` | 1 | 1,819 | 纯 C++20，6 条命令 + TUI |
| 定义文本 `Definitions.h` + `defs/` | 1 + 110 | 966 + 约 60 KB | `defs/def_*.txt` 由 `tools/gen_definitions.py` 生成头文件 |
| 开发工具/冒烟 `tools/` | 45 | 2,700 | 约 30 个 `_*_smoke.cpp` + 3 个 `.py` + 2 个 `.ps1` |
| 文档 `Docs/` | 7 | 1,604 | API / CONTRIBUTING / OOP 设计 / 构建审阅 / 互译器规范 |

源码合计（排除 `x64/`、`Debug/`、`Release/`、`ignore/`、`.vs/`）：**155 文件 / 40,905 行**。

叶子记号的规模分布（决定了迁移工时的形状）：

| 行数区间 | 文件数 | 说明 |
|---|---|---|
| < 200 | 27 | 简单序列/文本记号，多数是家族基座的薄封装 |
| 200–400 | 17 | 中等 |
| 400–600 | 20 | 大，含独立解析/渲染 |
| 600+ | 13 | 特大（`ts_omega_dbms` 922、`ts2dbms` 861、`lpms` 856…），规则最绕 |

### 1.2 影响判断的八个事实

1. **引擎是纯函数**。`Header/**` 里 `cout/printf/fopen/ifstream` 出现 **0 次**——没有 I/O、没有全局可变状态、没有线程。这既是 F# 最舒服的形态，也意味着迁移可以做"同输入 → 同输出"的字节比对。
2. **它本来就是函数式代码的二次移植**。92 个头文件里 **24 个**在注释里注明"移植自 `ne-rewritten` 的 `*.ts`"，多份文件甚至逐字记录了对上游的偏离（如 `ts_omega_dbms.hpp` 明确写了"按用户要求去掉 ∞ 顶层元素"）。也就是说：**源语言是不可变树 + 判别联合（TS），C++ 版是这份语义的手工翻译。**
3. **C++ 版正在为"持久化不可变结构"付利息**：127 处 `shared_ptr`、906 处 `std::vector<int>`，`bm1ynss.hpp` 里用 `ColStack`/`ParStack` + `resize` 手工复刻 TS 的"活动栈随子树返回而 splice"。
4. **能力契约靠空指针**。`NotationCaps` 全是可空函数指针，`has_seq()/has_text()` 等就是判空；新增记号忘了接线 = 运行时才发现。
5. **注册表是模板元编程做的**。`TypeList` + `constexpr std::array<NotationMeta,119>` + `constexpr std::sort` + 递归 `RegStep`，文档里记录了 MSVC C7658 的规避方案，以及"用空壳隔离编译排错"的土办法。
6. **header-only，每个 TU 重解析 3.2 万行**。`registry.hpp` 把 92 个头文件全 include 进来；GUI 和 CLI 各一份，CLI 单 TU 需要 `/bigobj`（产物 obj 27 MB）。
7. **现有"黄金语料"已经过期**（详见 §3.6）：`list.txt` 是 114 项旧顺序基线，`samples.txt` 里 87 段 `fsalter` 调用的是 11-15 已删除的命令。
8. **性能不是瓶颈**：见 §3.2 实测。

## 2. F# 能真正解决的问题（逐条对应证据）

这一节只说"F# 在这里能省什么"，每条都指到具体代码。第 2.7 节会把这些收益折价——因为其中相当一部分 C++ 也能拿到。

### 2.1 把"不可表示的状态"变成不可能表示

`ts_omega_dbms.hpp` 里 TS 的联合类型：

```ts
Ordinal = { kind:'epsilon', expr } | { kind:'cnf', terms }
```

C++ 版（现状）：

```cpp
struct TsOmegaDbmsOrdinal {
    bool epsilon = false;          // 判别位
    TsOmegaDbmsExpr epsilon_expr;  // 只在 epsilon==true 时有效
    std::vector<TsOmegaDbmsCnfTerm> terms;  // 只在 epsilon==false 时有效
};
```

两个字段永远同时在场，任意组合都"合法"，正确性靠调用方自觉。F#：

```fsharp
type Ordinal =
    | Epsilon of Expr
    | Cnf of CnfTerm list
```

**收益**：非法状态在类型层面不存在；`match` 少写一个分支编译器会报错（现在少写一个 `if` 只会静默走错路径）。这类"判别位 + 双字段"结构在 24 个 TS 移植文件里是普遍形态，不是孤例。

### 2.2 结构化共享替代手工持久化

`bm1ynss.hpp` 的核心结构是 `PNodeC{ cols: vector<PColC> }`、`PColC{ shared_ptr<vector<int>> parr; PNodePtr sub; }`，配合注释"活动栈 push / 每层 for 后 resize（splice）与 TS 逐字一致"。它做的事，本质是：

- TS 里 `node.cols.map(...)` 返回新数组，旧数组自动不变 → 天然持久化；
- C++ 里没有这个默认，于是要靠 `shared_ptr` + `vector` 拷贝 + 手写栈生命周期来**模拟**。

F# 的不可变 `list`/记录默认就是结构共享，没法写出"忘了 splice 导致父下标错位"这类 bug。**收益**：省掉 127 处引用计数样板和这类"逐字复刻上游栈语义"的注释；同时消掉原子 refcount 开销（`shared_ptr` 拷贝是 atomic，GC 是普通写）。

### 2.3 能力契约与穷尽性

现状：`INotation` 的虚函数 + `NotationCaps` 的空指针。新增一个记号要同时保证：适配器模板选对、注册项加上、GUI/CLI 都能构造、能力位填对。
F#：把"记号 = 元数据 + 一个 `expand : Input -> string` 函数"做成记录/DU，注册就是一个 `string * Notation` 列表；新增能力（比如以后要加 `seq`）编译器会把所有消费点列出来。

**收益**：把"漏接线"从运行时异常变成编译错误。对 119 个记号、单人维护的项目，这条比"代码更短"重要得多。

### 2.4 注册与排序：模板元编程 → 普通代码

现在的编译期排序（`constexpr sort` + 递归 `RegStep`）是为了"按显示名首字符码位排序 + 顺序在编译期定死"。F# 里这就是：

```fsharp
let sorted = registry |> List.sortBy (fun (m, _) -> firstCodepoint m.DisplayName)
```

**收益**：消掉 C7658 那类"报错位置不在源头"的模板坑、消掉 27 MB 的 obj 与 `/bigobj`、消掉"空壳隔离编译"的调试土办法。这条是纯粹的开发者体验收益，不影响任何功能。

### 2.5 构建与调试回路

现状：改一行记号规则 → 重解析 92 个头文件；排错手段是 `tools/_xxx_smoke.cpp` 单文件编译（文档里记录了这个套路），外加 PR 前跑 174 段样例。
F#：增量编译（改一个文件只重编它和下游），`dotnet fsi` 直接 `#load` 单个模块、喂几个输入把中间结构打出来——**这正是调试 119 条晦涩规则最缺的东西**。

**收益**：把"改规则 → 看到结果"的回路从几十秒压到秒级。这是日常最高频的操作，也是这类项目最容易劝退人的地方。

### 2.6 测试：从"冒烟 + 快照"到"属性"

现状：约 30 个 `*_smoke.cpp` + 一份一次性语料，没有属性测试。而这类记号天然有一组不变量：

- `parse (render e) = e`（往返）
- `expand` 后再 `expand` 的项长度单调（基本列序列应逐步增长）
- 非法输入必须落在"错误分支"而不是抛异常/越界

F# 的 FsCheck 可以几行生成随机表达式，把这些不变量跑成 10 万次。**收益**：覆盖面从"手挑 174 段"变成"随机 10 万次 + 174 段定值"，而且随手写。

### 2.7 这些收益有多少是"F# 专属"的（折价）

必须诚实：**上面前 5 条里有 3 条，用 C++ 也能拿到相当一部分**——

| 收益 | C++ 能拿到的比例 | 手段 |
|---|---|---|
| 消除无效状态 | 高 | `std::variant` + `std::visit`（穷尽性靠 `static_assert` 兜一半） |
| 去掉 `shared_ptr` 树 | 高 | `EntryArena` 块分配 + 下标代替指针（文档已建议） |
| 能力契约 | 中 | `concept` + 必需成员，编译期报错 |
| 模板注册表简化 | 中 | 运行时 `std::vector` + 稳定排序，放弃编译期 |
| 增量编译 / REPL 调试 | **低** | C++ 无对等物（模块/REPL 都弱） |
| 属性测试 / 穷尽性检查 | 中 | 有 gtest + QuickCheck 移植，但穷尽性弱 |

**结论**：如果目标只是"结构清爽、少踩模板坑"，**10–20 人日的 C++ 定向重构能拿到 60% 的收益**（见 §4 方案 A+）。F# 真正不可替代的是后两条：**回路速度与类型系统兜底**——它们对单人长期维护的价值，恰恰最难用数字证明。

## 3. 代价与风险（量化）

### 3.1 人日成本模型

假设：你已完全熟悉记号语义（这是最大的一块隐性成本，已经被项目本身的 1,600 行文档和注释覆盖），F# 从"能写"到"能写生产代码"约 1 周。

| 项 | 计算 | 人日 |
|---|---|---|
| 基座 15 模块 / 6.3k 行（解析/渲染/父查找/高度/比较/注册/互译） | 15–25 | 15–25 |
| 叶子 77 个 / 26k 行 | 27×0.4 + 17×1.0 + 20×2.0 + 13×4.0 | 80–125 |
| CLI（6 命令 + TUI） | — | 4–6 |
| 一致性套件 + 差分/属性测试工具 | — | 5–8 |
| 互操作（子进程协议 或 AOT 导出） | — | 3–5 |
| **合计** | | **105–160（中位 ~130）** |

折算：全职 5–7 个月；业余每周 10–15 小时，**12–18 个月**。

**行数预期（别指望变短）**：F# 版大致是 C++ 的 0.6–1.1 倍，即 2–3.5 万行。解析器和渲染器的体积和 C++ 差不多，省下来的是引用计数样板和类型声明，多出来的是模式匹配的重复臂。**用"代码更短"作为理由是不成立的。**

### 3.2 性能：不是瓶颈，但"深度展开"要单独看

本机实测（同一台机器、仓库现有 `ExpanderCLI.exe`）：

| 场景 | 命令 | 耗时 | 说明 |
|---|---|---|---|
| 典型展开 | `expand pps "1,2,2,2,2" 2` | 6.6 ms | 含进程启动 |
| 文本型 | `expand bms-v4 "(0,0,0)(1,1,1)(2,2,2)(3,3,3)(2,2,2)(3,3,3)(1,1,1)(2,2,2)" 2` | 7.6 ms | 同上 |
| 重负载 | `expand omega-y-sequence "1,2,…(25 项)" 3` | 13.6 ms | 同上 |
| 纯计算（文档记录） | 同上，循环 2000 次取均值 | **0.575 ms/次** | `Docs/构建参数与代码审阅.md` §三 |
| 轻负载（文档记录） | 其余 5 个 bench 用例 | **0.02 ms/次** | 同上 |
| 连续展开 | `chain pps "1,2,2,2,2,2" 2 200` | 1,456 ms | 约 115 步 |

三条可用的推断：

1. **交互场景下语言性能毫无影响**。单击一次展开的预算是 0.5–15 ms，即使 F# 慢 5 倍也在 100 ms 以内，人眼无感。
2. **`chain` 这类批处理有风险**。今天 1.4 s，若慢 5 倍是 7 s；深度/大项数输入会线性放大。缓解手段现实中存在（`[<Struct>]` DU、数组而不是 list、避免字符串拼接、`StringBuilder`、必要时 `Span`），但**能不能压到 2 倍以内，只有 spike 能量化**——这是决策门要测的第二个数。
3. **AVX2 实测反而慢 15–17%**，官方结论是"热点是指针追逐 + 每节点堆分配 + 字符串拼接，没有可向量化的连续数组"。这条对 F# 是**利好信号**：它说明瓶颈在分配与指针追逐，而 .NET 的 bump 分配 + 分代 GC 在这类形状上并不天然吃亏（`shared_ptr` 的原子引用计数本身也是纯开销）。**但这是推断，不是实测。**

### 3.3 分发与运行时

| 项 | 现状 | F# 方案 | 影响 |
|---|---|---|---|
| 体积 | `ExpanderCLI.exe` 2.1 MB 原生单文件 | self-contained 约 10–12 MB；NativeAOT 约 5 MB（未验证） | 社区分发可接受，但"绿色单文件"卖点变弱 |
| 启动 | 约 6 ms（含解析 3.2 万行头的 JIT 前成本为 0） | framework-dependent 30–60 ms；AOT 约 10 ms（未验证） | CLI 被脚本循环调用时，30–60 ms 会明显拖慢 |
| 依赖 | 无 | 需要 .NET 运行时，或自带/AOT | 对"给别人一个 exe 就能跑"是退步 |

对 GUI 更尖锐：MFC 那 1.8k 行 + `.rc` + `Resource.h` + 图标 + 对话框流程**没法在 F# 里延续**。要换前端就得上 Avalonia/WPF，那是 30–60 人日的另一笔账，还要重做 119 项选择表、搜索打分、tag、参数框、定义查看的交互回归。

### 3.4 过渡期的双实现同步

迁移期间同一记号存在两份实现。若不设约束，必然出现"改了 C++ 忘了 F#"或反之。**唯一可行的压法是：语料即契约——两版跑同一份用例，逐字节比对，绿了才切换，切完立刻下线 C++ 那份。** 这也解释了为什么阶段 0 必须先做一致性套件，否则过渡期无法管理。

### 3.5 语义漂移风险（最贵的风险）

- 现有语料只覆盖 **87/119** 个记号、每个 2 个操作、手挑输入；**32 个记号零覆盖**。
- 语料里 **87 段 `fsalter`** 调用的命令已在 11-15 删除；`list.txt` 是 **114** 项旧顺序，而当前 `list` 输出 **119** 项且已按首字符码位重排。
- 也就是说：**这份语料现在既跑不起来、也不完整**。"重写后逐字节一致"在今天是**无法验证**的承诺。

这条不是"风险提示"，是"必须先解决的问题"。好消息是解决它很便宜（§5 阶段 0）。

### 3.6 回收期（纯经济性）

假设：当前年维护投入 3–5 人月（含加记号、语义变更、重构——从 11 月的改动密度看是合理量级）；F# 后效率提升 20–30%；迁移中位 130 人日 ≈ 6 人月。

> 回收期 ≈ 6 / (3.5 × 0.25) ≈ **6–8 年**（乐观档 4.5 年，保守档 10 年）

**所以：把 F# 重写当"省时间"的工程投资，回报率不合格。** 它的正当理由只能是以下之一（按可信度排序）：

1. **质量**：119 条晦涩规则的错误代价高，而类型系统和测试体系能把"静默错"变少。
2. **可持续性**：单人维护 3 万行手工持久化 C++ 是长期消耗；换语言是换掉这项慢性成本。
3. **个人/研究价值**：如果你本来就想把 F# 用起来，这个项目是极好的练手场（规则清晰、有黄金语料、纯函数）。
4. **为新产品让路**：如果你打算做跨平台/Web 前端，F# 内核是更好的底座——但这属于产品决策，与"重写"本身无关。

## 4. 方案对比

评分口径：5 = 最好。成本按 §3.1 的人日。风险指"做完发现不划算或做不完"的概率。

| 方案 | 内容 | 可维护性 | 扩展速度 | 正确性保障 | 性能 | 分发 | 成本 | 风险 | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| **A** 维持 C++ | 只做增量改进 | 2 | 2 | 2 | 5 | 5 | 1 | 1 | 现状继续，问题是慢性病不治 |
| **A+** C++ 定向重构 | arena 替 `shared_ptr`、`variant` 替判别位、运行时注册、修解析层越界 | 3 | 3 | 3 | 5 | 5 | **10–20 人日** | 1 | **性价比最高的一档**，能拿 60% 收益 |
| **B-lite** 混合引擎 | 只把最痛的 10–20 个记号迁 F#，其余留 C++ | 3 | 3 | 3 | 3 | 3 | 25–40 人日 | 3 | 可行但长期是两套栈，维护面变宽 |
| **B** 引擎 + CLI 迁 F#，GUI 保留 MFC | F# 内核 + 进程边界/C ABI，MFC 壳不动 | 5 | 5 | 4 | 3 | 2 | **105–160 人日** | 4 | **值得，但有条件**（§5） |
| **C** 全量 F#（含 Avalonia GUI） | 换语言 + 换前端 + 换验证体系 | 5 | 5 | 4 | 3 | 2 | 145–220 人日 | 5 | **不建议** |

补两条容易忽略的横向对比：

- **与"重写"相比，"分工"往往更划算**：GUI 1.8k 行、CLI 1.8k 行、引擎 32k 行——真正的痛点集中在引擎。把引擎抽成独立可执行/可链接的单元（今天 header-only 已经具备了），本身就能让 GUI 不再被引擎的编译期和语义变更拖着走。这件事在 C++ 里做只要几天。
- **与上游 TS 的关系**：C++ 版是 TS 的二次翻译。如果再写 F#，就是第三次翻译——但 F# 的判别联合/不可变语义**离 TS 更近**，从 TS 原文对照时心智负担低于 C++。如果上游 `ne-rewritten` 还在演进、你还要持续同步，这条会显著抬高 F# 的相对价值；若上游已冻结（现状看起来如此），这条收益打折。

## 5. 如果要做，推荐路径（含决策门）

### 阶段 0：一致性套件重建（1–2 天，**无论是否重写都该做**）

1. 用当前 `ExpanderCLI.exe` 生成**新**基线：`list` 全量 + 每个记号 ≥8 条用例（正常 / 边界 / 非法 / 深度 / 大项数），按记号分文件存放（`tests/conformance/<id>.txt`），带 `version` 头。
2. 写一个 `--update` / `--check` 双模式的差分脚本：`--update` 只在**有意改语义**时用，且必须在 commit message 里说明原因。
3. 给 `tools/_bench.cpp` 的哈希机制扩到全套件，让"语义一致性"和"性能回归"共用一次跑批。

判据：`check` 在任何一次重构前后都必须为 0 差异；`update` 必须人工审 diff。

### 阶段 1：3 个代表记号的 F# spike（2–4 天，**决策门**）

选三个代表，覆盖三种形状而不是随便挑：

| 记号 | 为什么选它 | 覆盖的能力 |
|---|---|---|
| `prss`（**最简单**） | 验证"基础设施 + 最小规则"能跑通，排除脚手架成本 | 序列 → 序列 |
| `bms-v4`（**矩阵文本**） | 验证文本解析/渲染往返 + 列结构 | 文本 → 文本 |
| `omega-y-sequence`（**最重**） | 验证性能与复杂父查找，对应 25 项 term=3 的 0.575 ms 基线 | 序列 → 序列 + 深展开 |

决策门的三个指标（**缺一不可**）：

| 指标 | 通过线 | 不通过的含义 |
|---|---|---|
| 字节一致率 | 套件全绿（含 20 组随机/边界输入） | 说明"语义可平移"这个前提不成立，立即停 |
| 端到端耗时比（同机同输入，F# vs C++） | ≤ 3×（重负载），≤ 1.5×（典型） | 说明 §3.2 的缓解手段不够，深度展开场景不可接受 |
| 单记号工时 | 中位 ≤ 1.5 人日/个（含写用例） | 按 77 叶子外推会超过 150 人日，ROI 进一步恶化 |

同时在这个 spike 里实测三个"未验证"项：F# 递归深度上限、GC 在大展开下的暂停、NativeAOT 是否可用（含 `printf`/反射依赖）。

### 阶段 2：按家族迁移（仅在阶段 1 通过后）

顺序必须是"自底向上"：`common/core` → 家族基座（15 个）→ 家族内叶子 → 特例（BMS/UPMS/MrSS）→ 注册表。

**按家族成批切换，一次只切一族**：一族的所有记号在套件上全绿 → 一次性把该族注册项指向 F# 实现 → 观察一段时间（含 GUI 手测）→ 下线该族 C++ 头文件。禁止"半族迁移"（同一个记号两版并存超过一周）。

### 阶段 3：CLI 切换 + GUI 边界定型

- CLI：直接换成 F# 实现，命令字符串、错误文本、`list` 顺序逐字符对齐（这是最容易做、最没有争议的一步）。
- GUI：**保持 MFC 不动**。两种边界方案：
  - **推荐**：子进程 + 文本/JSON 协议（展开是纯 `text → text`，天然适配；代价是 10–30 ms/次，交互无感，且自带故障隔离与回滚开关）。
  - 备选：NativeAOT 编译成 `dll`，MFC 侧用 C ABI 调用（省掉进程开销，但要走一遍"F# → 导出符号"的可行性验证，风险高于收益）。
- 只有当你同时决定"要跨平台 / 要换 UI"时，才考虑 Avalonia——那是独立立项，不要混进这次迁移。

### 阶段 4：C++ 下线与文档同步

每族下线时同步：`Docs/API.md` 对应章节、`CONTRIBUTING.md` 的"记号实现位置"、`registry.hpp` 的注册项，以及 `defs/` 定义文本。

### 工程约定（六条，缺一条都会让过渡期失控）

1. **语料即契约**：没有用例覆盖的记号，一律不迁移。
2. **一次只动一个维度**：不同时改语义、改语言、改 UI。要改语义，先在 C++ 里改 + `--update` 语料，再迁。
3. **性能基线随迁**：每族迁移时重跑 `_bench` 对应用例，把比值记进族级 README。
4. **注释与需求随迁**：24 个 TS 移植文件里的"与上游的偏离/用户要求"必须原样搬进 F# 注释——这些注释是需求，不是废话。
5. **回滚开关**：每个记号保留"C++ / F#"选择位（配置文件或编译期开关），至少保留一个版本周期。
6. **不要在 F# 里重建模板魔法**：注册表就是列表 + `sortBy`，不要为了"编译期确定"再造 type-level 技巧。

## 6. 什么情况下结论会变

| 触发器 | 结论变化 |
|---|---|
| 你打算再做 **5 年以上**、每年新增 ≥10 个记号 | B 从"有条件"变成"推荐"（扩展速度与穷尽性收益被摊薄得足够快） |
| 你打算发布**跨平台/Web 版**或做教学配套 | C 变得合理（F# 内核 + 多前端是真需求，不是借口） |
| 上游 `ne-rewritten` 恢复活跃、需要持续同步 | F# 相对价值上升（判别联合语义离 TS 更近，二次翻译成本更低） |
| 你只是想"让代码更干净" | 走 **A+**（10–20 人日），不要走 B；差距是 10 倍成本换 1.3 倍收益 |
| 项目确实进入"只维护、不加记号" | **A**；重写是纯粹的沉没成本（README 写着"非活跃维护期"，但 dev 分支今天仍在改——这两句话矛盾，需要你自己确认哪个是真的） |
| 你本来的动机是"练 F#" | 阶段 0 + 阶段 1 已经足够（合计 3–6 天，产出真实可用）；不必为学习付 130 人日 |

## 7. 本评估未验证的点（诚实清单）

1. **F# 版真实性能**：§3.2 的耗时比是推断，不是实测；只看过 C++ 的 0.575 ms/0.02 ms 基线与 AVX2 的负收益结论。
2. **NativeAOT + F#** 的可用性与体积（`printf`/反射相关限制未知）。
3. **Avalonia 重写 GUI 的真实成本**（30–60 人日是按 1.8k 行 MFC + 资源/对话框类比的粗估，未做 spike）。
4. **迁移工时**：105–160 人日是"熟悉语义 + 会 F#"假设下的中位估计，唯一可靠的校准方式是阶段 1 的 3 个记号。
5. **CLI 启动开销对比**：只测了现有exe 的 6–14 ms，没测 F# framework-dependent 的真实冷启动。
6. **本机单 TU 编译耗时**：尝试实测时因 SDK 头文件路径问题未取到数字；只确认了结构事实（每 TU 重解析 92 头文件、obj 27 MB、需 `/bigobj`）。
